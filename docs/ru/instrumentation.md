# Инструментация

Что даёт каждый компонент, чего это стоит и какие его опции имеет смысл менять. Все ключи со
значениями по умолчанию — в [`config/example_config.yaml`](../../config/example_config.yaml).

Телеметрия следует семантическим соглашениям OpenTelemetry `1.44.0`, которые публикуются как
`schema_url` scope'а.

## Как настраиваются компоненты

Каждый компонент — один узел с двумя сигналами:

```yaml
open_telemetry:
    instrumentation:
        http_server:
            traces: true
            metrics: true
```

Над ними стоят два главных переключателя. При `traces.enabled: false` или
`metrics.enabled: false` ни один компонент не производит этот сигнал, что бы ни было написано в
его собственном ключе.

Там, где сигналу нужны свои опции, тот же ключ принимает длинную форму, а короткая в неё
нормализуется. Существует это ради одной настоящей асимметрии: healthcheck — шум в трейсе и
нагрузка в метрике.

```yaml
http_server:
    traces:
        enabled: true
        excluded_paths: ['/_profiler', '/_wdt', '/health']
    metrics:
        enabled: true
        excluded_paths: ['/_profiler', '/_wdt']
```

Компонент подключается только тогда, когда его компонент Symfony действительно установлен.
Проверяется то, что останется при установке с `--no-dev`, а не то, что `class_exists()` видит
сейчас.

У каждого компонента, записывающего длительность, есть ещё `duration_buckets` — см.
[Границы гистограмм](#границы-гистограмм).

## HTTP-сервер

*По умолчанию: трейсы включены, метрики включены.*

| | |
|---|---|
| Спаны | один серверный спан на основной запрос, имя `{method} {route}` — например, `GET /orders/{id}` |
| Атрибуты | `http.request.method`, `http.route`, `http.response.status_code`, а также `client.address` и `user.*` при явном включении |
| Метрики | `http.server.request.duration`, размеры тела запроса и ответа |

```yaml
http_server:
    excluded_paths: ['/_profiler', '/_wdt', '/health']
    record_client_ip: false
    record_user_id: false
    record_user_roles: false
    record_exception_min_status: 500
```

Имена спанов используют шаблоны маршрутов, а не сырые пути: `/orders/{id}` — один ряд,
`/orders/17` — миллион.

4xx оставляет статус спана незаданным. Соглашения ставят порог ошибки на 500, и спан им следует.
`record_exception_min_status` управляет только тем, с какого статуса исключение записывается
событием спана.

### Аутентифицированный пользователь

С установленным `symfony/security-core` серверный спан может нести того, кто сделал запрос.
Ключей два, потому что это два разных решения.

`user.id` называет человека. Трейс, который его несёт, становится персональными данными — с
обязательствами по хранению, доступу и удалению, — а бэкенд трассировки редко регулируется так же
строго, как собственная база приложения.

`user.roles` называет группу и отвечает на вопрос, который к трейсу обычно и задают: это было
медленно для админов или для всех. Этот ключ может включить большинство приложений.

Значение — `UserInterface::getUserIdentifier()` как есть, без хеширования. Хеш с солью от этого
пакета не был бы ни обратимым для поддержки, ни стабильным между развёртываниями, а для
приложений, считающих настоящий хеш, есть `user.hash`.

Пишется на `kernel.controller`, потому что на том приоритете, где открывается серверный спан,
firewall ещё не аутентифицировал. Размечается только основной запрос: подзапрос идёт внутри того
же трейса, а две личности на одном трейсе хуже, чем ни одной.

Токен берётся из `security.untracked_token_storage` и читается только тогда, когда есть спан,
куда его записать. `security.token_storage` учитывает чтения, и одно чтение за ленивым firewall
увеличивает индекс использования сессии. `AbstractSessionListener` отвечает на это заголовками
`Cache-Control: private, must-revalidate` и `max-age=0` на каждом ответе, включая те, которые
приложение намеренно сделало публичными. Включение этого ключа не меняет того, что отдаёт
приложение.

## HTTP-клиент

*По умолчанию: трейсы включены, метрики включены.*

| | |
|---|---|
| Спаны | один клиентский спан на запрос, имя по методу |
| Propagation | контекст трейса добавляется в исходящие заголовки, вызываемый сервис продолжает трейс |
| Метрики | `http.client.request.duration`, размеры тела запроса и ответа |

```yaml
http_client:
    excluded_hosts: ['otel-collector', 'alloy']
```

Ленивые и потоковые ответы обрабатываются жизненным циклом инструментации: спан закрывается,
когда ответ действительно завершён, а не когда клиент вернул управление.

Исключите коллектор, иначе телеметрия начнёт инструментировать собственный экспорт. Указывайте то
имя хоста, к которому приложение реально обращается: исключение `localhost` ничего не даёт, если
endpoint — `http://alloy:4318`.

## Doctrine DBAL

*По умолчанию: трейсы включены, метрики включены. Требуется DBAL 4.*

| | |
|---|---|
| Спаны | один на выражение, имя — сводка SQL; опционально по одному на границу транзакции |
| Метрики | `db.client.operation.duration` |

```yaml
doctrine:
    query_text: false
    only_with_parent: true
    transactions: true
```

`query_text` записывает выражение в `db.query.text`. Выключено по умолчанию, потому что сырой SQL
несёт литералы, а литералы несут данные о людях.

`only_with_parent` не пускает спаны запросов в трейсы, у которых нет родительской операции. Это
существует ради транспорта Messenger, опрашивающего базу каждую свободную секунду: эти запросы —
настоящая нагрузка, поэтому метрики записывают их в любом случае, но как трейсы это тысячи сирот
в сутки и ничего больше.

`transactions` делает `BEGIN`, `COMMIT` и `ROLLBACK` самостоятельными операциями: один спан на
round trip, с меткой `db.operation.name`. Без этого медленный или упавший commit сливается с тем
выражением, которое случайно оказалось перед ним. Вложенные транзакции — это savepoint'ы, и они
трассируются как выражения.

## Messenger

*По умолчанию: трейсы включены, метрики включены.*

| | |
|---|---|
| Спаны | `symfony.messenger.dispatch {Message}` на dispatch, producer-спан на отправку, consumer-спан на обработку сообщения |
| Propagation | контекст трейса едет с сообщением как stamp, поэтому отправка и обработка — один трейс |
| Метрики | отправлено сообщений, получено сообщений, `messaging.process.duration` |

Dispatch намеренно не измеряется как операция клиента очереди. Dispatch может провалидировать,
открыть транзакцию и выполнить обработчик прямо в процессе, вообще не трогая брокер, и, засчитав
это в перцентили отправки, мы получили бы синхронную шину, которая якобы отправляет сообщения,
которых не отправляла. Настоящая отправка измеряется отдельно, по транспортам, внутри спана
dispatch.

Единица работы — сообщение, а не воркер. Почему — см. [Console](#console).

## Console

*По умолчанию: трейсы включены, метрики выключены.*

| | |
|---|---|
| Спаны | один на команду, с кодом выхода и ошибкой, если она была |
| Метрики | `console.command.duration`, при `metrics: true` |

```yaml
console:
    excluded_commands: ['cache:clear', 'cache:warmup', 'assets:install', 'lint:container', 'lint:yaml']
```

Задание списка заменяет эти значения по умолчанию, но никогда — воркеры Messenger:
`messenger:consume` и `messenger:consume-messages` исключены всегда. Спан, покрывающий весь
процесс воркера, не экспортируется никогда, потому что спаны экспортируются при завершении, а
завершение здесь равно выходу процесса. Кроме того, он поглощает каждое сообщение в один
неограниченный трейс и обессмысливает `doctrine.only_with_parent`: всегда активный спан делает
холостой опрос похожим на работу внутри единицы работы.

## Cache

*По умолчанию: трейсы включены, метрики включены.*

| | |
|---|---|
| Спаны | один на операцию пула, имя `cache.{operation}` |
| Метрики | `cache.operation.duration`, `cache.lookup.count` с атрибутом hit/miss |

```yaml
cache:
    pools: ['*']
    excluded_pools:
        - cache.system
        - cache.validator
        - cache.serializer
        - cache.property_info
        - cache.messenger.restart_workers_signal
```

`['*']` берёт каждый поддерживаемый пул с тегом `cache.pool`, `[]` — ни одного. Исключённые по
умолчанию — собственные пулы фреймворка: инфраструктура, а не поведение приложения.

## Serializer

*По умолчанию: трейсы включены, метрики выключены.*

| | |
|---|---|
| Спаны | `serializer.{operation}` |
| Метрики | `serializer.operation.duration`, при `metrics: true` |

Спаны требуют существующего трейса. Работа вне трейса всё равно попадает в метрику длительности —
так происходит, когда Messenger декодирует сообщение до начала обработки. Метрики выключены по
умолчанию, потому что сериализация обычно достаточно видна внутри спана, который её содержит.

## Mailer

*По умолчанию: трейсы включены, метрики выключены.*

| | |
|---|---|
| Спаны | один на отправку транспортом |
| Метрики | `mailer.send.duration`, при `metrics: true` |

```yaml
mailer:
    record_subject: false
```

Темы писем — пользовательский контент, и в них регулярно попадает человек или номер заказа.

## Scheduler

*По умолчанию: трейсы включены, метрики выключены.*

| | |
|---|---|
| Спаны | `scheduler.run` вокруг запланированной задачи внутри обработки сообщения, с `scheduler.schedule.name`, `scheduler.task.id` и типом сообщения |
| Метрики | `scheduler.task.duration`, при `metrics: true` |

## Monolog

Две независимые вещи:

```yaml
open_telemetry:
    logs:
        correlation:
            enabled: true     # trace_id и span_id в каждой записи
        export:
            enabled: false    # сами записи, по OTLP
```

Корреляция — это то, что позволяет найти строку лога из трейса и трейс из строки. Экспорт —
вторая точка назначения для каждой строки; см.
[Конфигурацию](configuration.md#коррелируйте-и-экспортируйте-логи).

Всё, что пакет сообщает о себе, идёт в канал Monolog `open_telemetry`, и туда же направлен вывод
самого SDK. Без этого SDK откатывается на `error_log()`, и «коллектор отверг batch» оказывается
вне логирования приложения, тогда как собственные сообщения пакета остаются внутри. Этот канал не
экспортируется по OTLP никогда, что бы ни было в `logs.export.excluded_channels`.

## PHP-рантайм

*По умолчанию: метрики включены. Трейсов нет: здесь нет операции, есть только состояние.*

| | |
|---|---|
| Метрики | `php.memory.usage` (куча Zend-аллокатора) и `php.worker.uptime`, снимаемые при каждом экспорте |

В worker-режиме это единственное место, где видна медленная утечка памяти, потому что коллектор,
скрапящий хост, видит один долгоживущий процесс, а не его кучу. Воркеры различаются по
`service.instance.id` в ресурсе, а не по метке на этих метриках.

Их публикуют только процессы, обслуживающие работу многократно: HTTP-воркер, цикл
`messenger:consume`. Одноразовая консольная команда не начинает вовсе — её двухсекундная жизнь
это шум в ряду, который должен показывать медленный рост.

## Границы гистограмм

Каждый компонент, записывающий длительность, принимает `duration_buckets` в секундах:

```yaml
open_telemetry:
    instrumentation:
        doctrine:
            duration_buckets: [0.0005, 0.001, 0.005, 0.01, 0.05, 0.25]
```

Значения по умолчанию следуют семантическим соглашениям, а те выбраны так, чтобы быть сравнимыми
между сервисами, а не плотными вокруг какого-то одного. SLO, сформулированный в единицах
миллисекунд, не виден в корзинах, у которых второй шаг — 10 мс.

Границы должны строго возрастать и быть больше нуля. Всё остальное отклоняется при компиляции
контейнера, потому что SDK построил бы корзины как есть и гистограмма тихо перестала бы
что-либо значить. Пустой список сохраняет значения по умолчанию. Единица остаётся секундой:
гистограмму, у которой единица разная по компонентам, нельзя сравнивать между компонентами.

Для того, до чего это не дотягивается — инструмента, созданного не пакетом, или ключа атрибута,
кардинальность которого нужно срезать, — есть [metric view](sdk-customization.md#добавить-metric-view).

## Propagation в ответе

По умолчанию вызывающей стороне ничего не возвращается. Задайте
`OTEL_EXPERIMENTAL_RESPONSE_PROPAGATORS` и установите пакет-пропагатор, который регистрирует себя
в SDK, чей собственный реестр знает только `none`. Тогда пакет добавит полученные заголовки в
ответ основного запроса.

В подзапросы это не идёт. Их ответ рендерится в страницу, а не отправляется, и делать это на
каждый подзапрос значило бы перезаписать заголовок основного запроса внутренним спаном. Заголовок
называет серверный спан, а не спан вызывающего.

Контракт на стороне SDK помечен экспериментальным; пакет подключает его осознанно.

## Чувствительные данные и кардинальность

Атрибуты спанов и метки метрик заслуживают разных ответов. Идентификатор запроса, заказа или
пользователя в трейсе может быть ровно тем, что нужно расследованию. Тот же идентификатор в
атрибуте метрики — новый временной ряд, навсегда.

Пакет никогда не копирует атрибут спана в метку метрики. Включение любого захвата меняет
содержимое трейса и не меняет количество рядов.

Каждый захват, способный идентифицировать человека, — opt-in, и у каждого свой ключ, чтобы
решение принималось по одному разу на вид, а не один раз на все:

| Ключ | Что записывает | По умолчанию |
|---|---|---|
| `doctrine.query_text` | `db.query.text` — сырой SQL вместе с литералами | выкл |
| `http_server.record_client_ip` | `client.address` | выкл |
| `http_server.record_user_id` | `user.id` из аутентифицированного токена | выкл |
| `http_server.record_user_roles` | `user.roles` — группа, не человек | выкл |
| `mailer.record_subject` | темы писем, то есть пользовательский контент | выкл |

Прежде чем включать любой из них, решите, где хранятся трейсы, кто может их читать и сколько они
живут. Бэкенд трассировки редко регулируется так же строго, как собственная база приложения, а на
трейс обычно не распространяется политика хранения, написанная для этой базы.
