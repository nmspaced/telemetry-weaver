# Конфигурация

Здесь собраны решения, которые стоит принять осознанно перед продакшеном. Каждый раздел решает
одну задачу; читайте нужные, в любом порядке. Все ключи, которые понимает пакет, со значениями по
умолчанию — в [`config/example_config.yaml`](../../config/example_config.yaml).

## Два слоя, без пересечений

| | Отвечает за | Задаётся |
|---|---|---|
| OpenTelemetry SDK и экспорт | endpoint, протокол, заголовки, sampler, экспортёры, размеры очередей, интервалы, детекторы ресурса | переменные `OTEL_*` / `OTEL_PHP_*` |
| Пакет | что инструментируется, что записывается, бюджет flush на границе | `config/packages/open_telemetry.yaml` |

Ни один ключ пакета не дублирует переменную `OTEL_*`. Там, где пакет принимает id сервиса для
sampler'а, экспортёра или провайдера, это не дублирование: переменная выбирает из реализаций,
которые SDK уже знает, а id передаёт конвейеру ту, которой он не знает.

## Экспортируйте в локальный коллектор

Отправляйте телеметрию коллектору на том же хосте — в sidecar или в локальной сети, — а с
удалённым бэкендом пусть разговаривает он.

```text
PHP-воркер
   │ короткая, ограниченная передача по OTLP
   ▼
Collector / Alloy, локально
   │ очереди, ретраи, учётные данные, маршрутизация
   ▼
удалённые бэкенды
```

Это [agent pattern], и он даёт четыре вещи:

- задержка OTLP для приложения остаётся маленькой и предсказуемой;
- удалённые ретраи и очереди происходят вне PHP, где они не блокируют воркер;
- учётные данные бэкендов лежат в одном месте, а не в каждом приложении;
- недоступность бэкенда становится проблемой коллектора, а не запроса.

Экспорт напрямую в удалённый SaaS-endpoint работает, но таймауты поднимайте осознанно. Telemetry
Weaver ограничивает стандартный транспорт, но не сокращает сетевой round trip, и это не надёжная
очередь: телеметрия, не поместившаяся в бюджет, отбрасывается намеренно.

[agent pattern]: https://opentelemetry.io/docs/collector/deploy/agent/

## Выберите протокол

Берите **HTTP/protobuf**, если нет причин поступить иначе. Это значение по умолчанию и самый
простой вариант:

```dotenv
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318
```

Нужны `open-telemetry/exporter-otlp`, PSR-18-клиент и PSR-17-фабрика.

Берите **gRPC**, когда окружение уже на нём:

```bash
composer require open-telemetry/transport-grpc   # требует ext-grpc
```

```dotenv
OTEL_EXPORTER_OTLP_PROTOCOL=grpc
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4317
```

Бюджет действует одинаково для обоих. Проверьте путь через gRPC в настоящем образе развёртывания,
особенно TLS и восстановление после перезапуска коллектора.

## Настройте два таймаута

```dotenv
OTEL_EXPORTER_OTLP_TIMEOUT=500
```

```yaml
open_telemetry:
    sdk:
        export:
            flush_timeout_ms: 1000
```

`OTEL_EXPORTER_OTLP_TIMEOUT` — потолок одной отправки по OTLP. `flush_timeout_ms` — общий дедлайн
одной границы выполнения, покрывающий все сигналы, которые этой границе нужно отправить. Граница —
это конец запроса, завершившаяся команда или воркер между сообщениями. Каждая отправка получает
меньшее из двух значений.

Когда коллекторов несколько, дедлайн границы делится между ними, а не умножается на их число.
См. [Устойчивость экспорта](export-resilience.md).

Начните с 250–500 мс на отправку и 500–1000 мс на границу для локального коллектора, затем
измеряйте. Удалённый коллектор, которому нужны целые секунды, лучше придвинуть к приложению, чем
выдавать ему всё большую долю каждого запроса.

## Держите ретраи вне PHP

```yaml
open_telemetry:
    sdk:
        export:
            max_retries: 0    # по умолчанию
```

Стандартный PHP-транспорт повторяет попытки синхронно, поэтому каждая спит в вызывающем процессе.
Когда коллектор лежит, три ретрая превращают одну неудачную отправку в несколько таймаутов плюс
backoff, внутри воркера, который должен обслуживать трафик. Потерять эту телеметрию дешевле.

Ретраи и очередь отправки настраивайте на коллекторе, где они асинхронны.

## Сэмплируйте и ставьте трейсы в очередь

```dotenv
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1

OTEL_PHP_TRACES_PROCESSOR=batch
OTEL_BSP_SCHEDULE_DELAY=1000
OTEL_BSP_MAX_QUEUE_SIZE=2048
OTEL_BSP_MAX_EXPORT_BATCH_SIZE=512
```

Решите вопрос сэмплирования до того, как ужимать очереди под объём.
`parentbased_traceidratio` сохраняет решение, пришедшее снаружи, и сэмплирует новые корневые
трейсы с заданной долей. В локальной разработке используйте `always_on`.

Пакет строит batch-процессор с выключенным авто-flush. `span->end()` только ставит спан в
очередь, а очередь опустошается на границах выполнения: по истечении задержки расписания или на
первой границе, где уже ждёт полный батч. Спаны, переполнившие очередь внутри одной единицы работы,
отбрасываются, а не экспортируются на месте: ограниченная потеря вместо неограниченной очереди или
сетевого ожидания внутри бизнес-кода. Следующая граница пишет о потере в лог. Размер очереди
рассчитывайте на самый тяжёлый запрос, сообщение или команду **одного воркера**.

`OTEL_PHP_TRACES_PROCESSOR=simple` — сознательный отказ от всего этого: экспорт происходит в
момент завершения спана, что возвращает задержку коллектора на путь запроса.

Когда решение о сэмплировании не выражается ни одним sampler'ом из SDK — никогда этот
healthcheck, всегда оформление заказа, пять процентов остального, — настройте свой сервис и
сохраните всё, что пакет строит вокруг него:

```yaml
open_telemetry:
    sdk:
        traces:
            sampler: App\Telemetry\PerRouteSampler
```

См. [Кастомизацию SDK](sdk-customization.md).

## Задайте частоту и temporality метрик

```dotenv
OTEL_METRIC_EXPORT_INTERVAL=15000
```

Метрики экспортируются на границах выполнения, и каждый экспорт — блокирующая отправка. Интервал
и есть то, что не даёт нагруженному приложению экспортировать на каждой границе.
`metrics.flush_interval_ms: null` следует за `OTEL_METRIC_EXPORT_INTERVAL`, за тем же, на чём
экспортёр работал бы и сам; задавайте значение, только чтобы флашить *реже*.

Temporality следует выбранному предпочтению SDK, но по инструментам, а не одной настройкой на
всех:

```dotenv
OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta
```

При `delta` счётчики и гистограммы дельтовые. Up-down-счётчики и состояние остаются
кумулятивными: у них смысл — текущее значение, и потребитель не должен проигрывать все дельты с
момента старта процесса, чтобы узнать, сколько памяти занимает воркер.

Если бэкенду дельты не нужны, оставьте значение SDK по умолчанию.

## Коррелируйте и экспортируйте логи

Корреляция добавляет `trace_id` и `span_id` в записи лога, чтобы строку можно было найти из
трейса, а трейс — из строки. Ниже по конвейеру она ничего не стоит и включена по умолчанию.

Экспорт самих записей по OTLP — это вторая точка назначения для каждой строки лога, и он
выключен:

```yaml
open_telemetry:
    logs:
        correlation:
            enabled: true
        export:
            enabled: false
```

Оставьте экспорт выключенным, когда логи и так доезжают до Loki, Elastic или journald. Чтобы
включить, нужны `symfony/monolog-bundle`, потому что handler встраивается в собственный стек
Monolog, и названный экспортёр:

```dotenv
OTEL_LOGS_EXPORTER=otlp
OTEL_BLRP_SCHEDULE_DELAY=1000
OTEL_BLRP_MAX_QUEUE_SIZE=2048
OTEL_BLRP_MAX_EXPORT_BATCH_SIZE=512
```

```yaml
open_telemetry:
    logs:
        export:
            enabled: true
            level: info                  # не debug: отгружать каждую debug-строку — решение про трафик
            excluded_channels: []
```

Экспорт логов устроен так же, как трейсы — очередь и опустошение на границе, — поэтому запись
строки лога не ждёт коллектор.

Канал `open_telemetry` не экспортируется никогда, что бы ни было в этом списке. Запись о
неудачном экспорте, экспортированная наружу, снова наполняет очередь, из-за которой сбой и
произошёл.

## Отправьте каждый сигнал на свой endpoint

Один локальный коллектор — простой случай. Для OTLP/HTTP SDK сам выводит `/v1/traces`,
`/v1/metrics` и `/v1/logs` из базового адреса:

```dotenv
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318
```

Endpoint'ы по сигналам используются ровно как написано, поэтому путь сигнала нужно указывать:

```dotenv
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://tempo:4318/v1/traces
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://mimir:4318/v1/metrics
OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://loki:4318/v1/logs
```

Три хоста — три независимых домена отказа, и бюджет flush так их и рассматривает. Три пути на
одном хосте — один домен.

## Аутентифицируйтесь на коллекторе

```dotenv
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer%20token
```

`sdk.exporter_otlp_headers` накладывается поверх этой переменной для OTLP-транспортов пакета.
Записи оттуда выигрывают при совпадении, а значение `null` убирает заголовок, заданный
переменной. Собственное семейство транспортов отвечает за свою аутентификацию само и этого
слияния не видит.

## Объявите runtime mode и идентичность воркера

Переживает ли конвейер запрос — не настройка пакета. Это следует из `kernel.runtime_mode.web` и
`kernel.runtime_mode.worker` Symfony, вычисленных из `APP_RUNTIME_MODE`. Не выводите это из
`PHP_SAPI`.

| Рантайм | Режим | На границе |
|---|---|---|
| PHP-FPM, одно PHP-исполнение на запрос | `web=1&worker=0` | flush и завершение конвейера на terminate |
| Общий HTTP-воркер (FrankenPHP, RoadRunner) | `worker=1` | flush на каждый запрос, shutdown при выходе процесса |
| Воркер, пересобирающий ядро на каждый запрос | `worker=2` | завершение конвейера на каждый запрос, идентичность воркера сохраняется |
| Console, Messenger | — | flush на команду или сообщение, shutdown при выходе процесса |

FrankenPHP работает с этой моделью из коробки. Для собственной интеграции с RoadRunner или своего
bootstrap проверьте итоговые параметры: общий HTTP-воркер должен выглядеть как `web=1&worker=1`,
что можно задать явно.

```dotenv
APP_RUNTIME_MODE=web=1&worker=1
```

Долгоживущие воркеры получают стабильный `service.instance.id` от детектора SDK — именно он
отличает два воркера одного сервиса. Задавайте его руками, только если можете гарантировать
уникальность на каждый одновременно работающий воркер. Одинаковое имя хоста на всех процессах
делает их ряды неразличимыми, что хуже сгенерированного значения.

## Экспортируйте метрики из рантайма «процесс на запрос» (FPM, `FRANKENPHP_RESET_KERNEL`)

PHP-FPM и FrankenPHP с `FRANKENPHP_RESET_KERNEL=1` на каждый запрос строят новый контейнер, а
вместе с ним и новый MeterProvider. Кумулятивный счётчик из такого конвейера на каждом запросе
начинается с нуля, поэтому **метрики из этих рантаймов по умолчанию выключены**. Трейсы и логи это
не затрагивает.

Экспортировать их можно при двух условиях: приложение отправляет **delta**-temporality, и где-то
ниже по конвейеру delta превращается обратно в cumulative, если этого требует бэкенд.

### 1. Включить delta

```yaml
open_telemetry:
    runtime:
        request_metrics:
            mode: delta    # по умолчанию: disabled
```

Тогда каждый запрос один раз, после отправки ответа, экспортирует то, что записал:

- Счётчики и гистограммы идут DELTA-потоками. Каждый ребёнок FPM, или поток воркера FrankenPHP, —
  один поток, который продолжается через все обслуженные им запросы.
- UpDownCounter и gauge остаются кумулятивными и описывают один этот запрос.
- `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE` здесь не действует. Она по-прежнему
  управляет долгоживущими процессами.

**Идентичность писателя.** Бэкенд должен различать потоки. Под FPM пакет выводит для каждого
ребёнка стабильный `service.instance.id`: UUID v5 от `container.id`, `host.id`, `host.name` и
`process.pid`. Он одинаков на всех запросах одного ребёнка и различается между детьми. Важнее
всего это для маппинга Prometheus, где `instance` берётся из `service.instance.id` и ни из чего
больше; без него все дети писали бы в одну серию. У потоков воркера FrankenPHP уже есть свой id
на поток от SDK. Заданный вами id через `OTEL_RESOURCE_ATTRIBUTES` или `sdk.resource_attributes`
всегда побеждает, и он всё равно должен быть уникален для каждого ребёнка: один
`service.instance.id=${HOSTNAME}` на весь пул — ровно тот случай, который всё ломает.

Для вывода id нужен детектор SDK `process` и хотя бы один из `host` или `container`. Значение SDK
по умолчанию `OTEL_PHP_DETECTORS=all` их включает, а `env,host,process,process_runtime,sdk` —
безопасный явный набор. Без них id не выводится, а метрики всё равно экспортируются.

Пакет не проверяет, принимает ли бэкенд delta и различаются ли писатели. Правильная настройка
принимающей стороны — ответственность развёртывания.

### 2. Преобразовать delta в cumulative в коллекторе

Prometheus, Mimir и всё, что получает данные через Prometheus remote write, хранят кумулятивные
ряды. Поставьте перед ними процессор коллектора `deltatocumulative`:

```yaml
processors:
    deltatocumulative:
        max_stale: 5m
        max_streams: 100000

service:
    pipelines:
        metrics:
            receivers: [otlp]
            processors: [memory_limiter, deltatocumulative, batch]
            exporters: [otlphttp/prometheus]
```

Полная проверенная конфигурация лежит в
[`config/examples/collector.yaml`](../../config/examples/collector.yaml). В ней важны три вещи:

- **Процессор хранит состояние каждого потока, поэтому все точки одного потока должны попадать в
  один и тот же экземпляр коллектора.** Запускайте коллектор агентом: sidecar'ом или по одному на
  узел, куда шлют поды этого узла. Пулу шлюзов нужен экспортёр `loadbalancing` с
  `routing_key: streamID` перед ним. Round-robin между коллекторами с состоянием молча даёт
  неверные суммы.
- `max_stale` ограничивает, сколько помнится поток без новых точек. Ребёнок, перезапущенный по
  `pm.max_requests`, перестаёт писать, и его ряд заканчивается через этот интервал. `max_streams`
  ограничивает память: примерно дети на хост × хосты × ряды на ребёнка. Потоки сверх лимита
  отбрасываются.
- Бэкенду, который принимает delta нативно, процессор не нужен. Отправляйте данные как есть.

### 3. Во что это обходится

- **Один экспорт метрик по OTLP на каждый запрос**, после отправки ответа. Он укладывается в
  бюджет границы (`sdk.export.flush_timeout_ms`), но коллектор получает столько же запросов,
  сколько получает PHP.
- **Отдельная серия на каждого ребёнка FPM**, плюс новые серии при каждом перезапуске детей.
  Агрегируйте в запросах, например
  `sum without (instance) (rate(http_server_request_duration_seconds_count[5m]))`. Высокий или
  неограниченный `pm.max_requests` уменьшает эту текучку.

Метрики воркера (`php.memory.usage`, `php.worker.uptime`) в этих рантаймах не пишутся никогда,
потому что у конвейера, живущего один запрос, нет состояния воркера, о котором можно сообщить.

## Оставьте debug scopes включёнными в разработке

`open-telemetry/context` оборачивает каждую активацию контекста в debug-scope под `assert()`: это
объект на каждый спан и сообщение о scope, отцепленном не по порядку. При `zend.assertions=1`,
значении по умолчанию для разработки, такие сообщения стоит читать: вся модель владения в этом
пакете как раз про scope'ы, которые не должны пережить открывшую их работу.

В продакшене `zend.assertions=-1` вырезает assert целиком, и вопрос не возникает. Если
разработческий воркер нагружен настолько, что накладные расходы заметны, отключите именно
обёртку:

```dotenv
OTEL_PHP_DEBUG_SCOPES_DISABLED=true
```

Не ставьте это там, где вы хотели бы узнать об утёкшем scope.

## Читайте собственную диагностику пакета

Упавшая инструментация, scope, закрытый не по порядку, неудачный экспорт — всё это идёт в канал
Monolog `open_telemetry` с ограничением частоты, вместе с выводом самого SDK:

```yaml
open_telemetry:
    diagnostics:
        enabled: true
        detailed_per_process: 10
        min_interval_seconds: 60.0
```

`diagnostics.enabled: false` заглушает и SDK, а не возвращает его в `error_log()`.
